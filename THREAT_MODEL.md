# Remxo Threat Model (L1)

## Assets and trust boundaries

Assets include host inventory and connection metadata, Vault SSH passwords/private-key passphrases/imported private keys/sudo credentials, wrapped and unwrapped DEK, KEK/master and backup passwords, external Agent signing access, approval intent, audit metadata, task/tunnel state, managed temporary key files and remote-output integrity.

The primary boundary is between an AI caller/local CLI and the same-user local Broker; other boundaries exist between Broker and its OpenSSH-invoked ASKPASS child, between a managed plaintext temporary key and OpenSSH, and between Remxo/OpenSSH and remote output. L1 is defense against accidents, **not isolation from malicious code running as the same user**. Loopback RPC, random tokens, restricted file modes and narrow Secret responses do not change that. A future L2 boundary is a distinct OS-user Broker with restricted IPC and independent human approval. L3 adds remote/central authorization and short-lived identities.

## Baseline assumptions

- The user intentionally unlocks Vault, imports the intended key file and approves dangerous operations.
- System OpenSSH and its host-key policy are trusted; unknown keys are not auto-accepted or answered through ASKPASS.
- The current Remxo executable and local OpenSSH/scp/sftp binaries are trusted. A same-user attacker who can replace them is outside L1.
- Remote software is not assumed safe just because Remxo quotes its command.
- Protected files are created with private permissions where the platform implementation supports them; sensitive writes are atomic where practical. Native Windows ACL equivalence is not assumed.
- Passwords/passphrases must transiently exist in process memory, same-user RPC and ASKPASS stdout. Imported private keys additionally require a plaintext managed temporary file for OpenSSH.
- root, kernel and remote-account compromise are outside the model. A malicious same-OS-user process can bypass virtually all L1 controls.

## Threats and controls

| Threat | Control in this version | Residual risk / required behavior |
| --- | --- | --- |
| Secrets enter ordinary AI operation results | Normal execute/task/transfer results do not contain Vault records; no secret-valued public CLI flags; output redaction and exact sudo echo stripping; masked `*` password UI without plaintext echo | Internal `SecretForAuth` deliberately returns one typed Secret for authentication, so “RPC only returns per-operation results” is false. Mask length and same-user AI/processes may inspect input/memory outside L1. Redaction is heuristic and arbitrary remote secrets remain possible. |
| Arbitrary Vault record exported through ASKPASS/RPC | Broker re-resolves the current registered Host, derives credential name from its stem, enforces `ssh-password`/`ssh-private-key` kind and returns only one Secret; no Vault-list/dump response | Loopback plus token is not same-user authorization. A malicious token holder/process can use internal methods or read Broker memory. Do not describe this as L2 or “secrets are never exported.” |
| Pending wizard context substitutes for a saved Host | Pending Host is used only for pre-save wizard authentication, is validated, and is rejected when its alias is already registered | Pending Host metadata travels in helper environment and must remain non-secret. Saved configuration may change between operations; Broker re-resolution is the security decision point. |
| Host edit silently invalidates the previous target or replaces its active key too early | Alias is fixed, expected-Host comparison rejects stale forms, nonsecret edits retain credentials, explicit replacements use a versioned credential stem; Save & test uses the saved registered Host, not pending context | A rotated record may remain encrypted after success, cancellation or failure; there is no cross-config/Vault transaction or automatic secure deletion. A test performed after saving never implies its failure rolled back that edit. |
| ASKPASS auto-answers a dangerous prompt | Current Remxo executable plus one prompt; helper accepts only bounded password/passphrase categories; rejects yes/no, host-key, fingerprint, continue-connecting, OTP, MFA, PIN, token and unknown prompts | Prompt-string filtering is intentionally narrow, not general natural-language understanding. OpenSSH/localization changes may fail closed. Never broaden it to host-key or MFA answers without a new human-verification design. |
| Secret leaks through helper launch metadata | `SSH_ASKPASS` is current executable; environment contains only config path, target alias and optional non-secret pending Host; no public `__askpass` subcommand; password goes only to helper stdout | Same-user process inspection can still expose non-secret metadata and intercept the broader process environment. Do not manually reuse internal entry as a general secret CLI or log its stdout. |
| Vault mode silently retries or falls back to another identity | Vault modes force `BatchMode=no`, ASKPASS and one password prompt; password mode disables pubkey/keyboard-interactive; key mode uses managed `-i`, `IdentitiesOnly=yes`, `IdentityAgent=none`, publickey only | Server/account policy and user OpenSSH configuration still affect connection behavior. Authentication failure is not evidence that a write did not happen; no automatic remote-operation retry is allowed. |
| External/OpenSSH noninteractive invocation hangs for credentials | `openssh-config` and `external-agent` use `BatchMode=yes` outside interactive flows; missing required external Agent fails explicitly | Interactive SSH/SFTP intentionally permits normal OpenSSH interaction. User OpenSSH configuration can still weaken or alter behavior. |
| Malicious/private-key source file | Regular-file-only import, symlink/directory/special-file rejection, 1 MiB metadata/read limits, ASCII and OpenSSH/RSA/EC/PKCS#8 PEM first-marker checks; original source not modified | Marker checks are not key parsing, decryption, proof of ownership or authorized-use validation. Import errors must not echo contents. Source path is non-secret visible metadata; source-file race/platform semantics require continued review. |
| Plaintext private key persists after use | Broker returns only the selected `ssh-private-key`; managed temp file under data-root runtime, Unix `0600`, guard held for child/tunnel lifetime and deleted on normal drop | Plaintext exists on disk during authentication. Crashes/kill may prevent cleanup and deletion is not secure erasure. Native Windows ACL enforcement and real authentication are not verified; do not extrapolate Unix guarantees. |
| Secret copies persist in memory/RPC | Small scoped request/response, zeroizing buffers where used, exact helper output only to OpenSSH pipe; no DEK returned | zeroize does not prove removal of compiler copies, JSON serialization copies, pagefile/core dumps, RPC buffers, stdout pipes or forensic residue. These plaintext channels are intentional L1 exposure, not encrypted transport claims. |
| Wizard failure leaves an unexpected partial state | Esc/failed Test does not save Host; Save persists Host only after SSH credential success; sudo happens separately after Host save | This is explicitly not transactional: imported SSH/key credentials remain encrypted in Vault after failed Test, direct Save failure or Esc; sudo failure leaves the saved Host. Users may need explicit remediation; documentation/UI must not claim rollback. |
| Unauthorized high-risk command | Per-host raw modes, profiles, `approval=never/writes/always`, bounded approvals, sudo approval | Raw allow confers remote account permissions. Read detection is intentionally conservative and not a sandbox. Same-user approval is L1 convenience. |
| Local command injection | `std::process::Command`/tokio argv; no local `sh -c`; connection fields validated | Untrusted local executable paths and compromised OpenSSH are outside the boundary. Test fakes must be isolated. The temp-key path is argv-visible by necessity, but key contents are not. |
| Remote raw-command injection | Multi-argument POSIX commands use single-argument quoting; single raw string is explicitly a shell script | Remote shell still interprets scripts/operators. Metacharacters in a single raw string are intended behavior, not escaped safety. |
| `--cwd` injection | `cd` uses POSIX single-quote escaping, never concatenates unquoted path | Only POSIX is supported. Other shell models fail unsupported rather than using wrong escaping. |
| Profile/template injection | Typed names, service regex, integer range 1–1000, duplicate/unknown argument rejection, shell quoting | Profiles are a fixed small allowlist, not arbitrary safe templating. |
| Unregistered IP bypass | Alias → number → registered IP resolution; ad-hoc disabled unless `allow_ad_hoc=true`; ad-hoc still uses policy/approval | Explicitly enabling ad-hoc widens the inventory boundary. Numeric aliases and duplicate numbers are rejected. |
| Approval forgery/modification/replay | In-memory random ID, SHA-256 digest of resolved host config, operation, script/paths and relevant limits, 5-minute expiry, explicit approval bit and single consumption | Same user can alter Broker memory or approve directly. L2 requires independent human approval; IDs are not portable authorization tokens. |
| Host-key disable | No `StrictHostKeyChecking=no`, `UserKnownHostsFile=/dev/null`, `ForwardAgent=yes`; host-key ASKPASS prompts fail; failures map to `host_key_failed` | Admin/user OpenSSH config may still weaken policy; a human must verify/register unknown hosts. Vault authentication never relaxes strict known_hosts. |
| Configuration/language recovery overwrites trust settings | Strict TOML unknown-field rejection, `en`/`zh-CN` enum, legacy default English; valid config-only recovery preserves original config/language and creates only missing Vault | JSON/non-TTY language default does not make hidden master-password init noninteractive. Invalid config or existing Vault fails closed; multi-file initialization is not a general transaction. |
| npm launcher silently selects an unrelated or incompatible native executable | os/arch package filtering, exact same-version manifests/native `--version`, vendored binary resolution; unsupported/missing/mismatched packages fail closed with no PATH fallback | A compromised package registry or malicious same-user replacement remains a supply-chain/local integrity threat, not an L2 boundary. Release/tarball checks do not prove code signing or all-platform installation. |
| Audit/error leakage | JSONL records metadata and request digests, no default full stdout/stderr or credential values; transferable content and remote errors are sanitized | Paths/metadata may be sensitive; same-user audit tampering is out of L1. Redaction cannot guarantee secret detection. Never log ASKPASS stdout or private-key contents. |
| Untrusted output control/prompt effects | Raw-byte cap, sanitization before final truncation, UTF-8-safe limit, terminal control escapes | Output remains untrusted natural language and can instruct an AI; control stripping is not prompt-injection prevention. |
| Unsafe transfer overwrite/path expansion | Broker policy and digest; default local overwrite refusal; default remote existence preflight; `--overwrite`/config policy; `scp -s` forces SFTP mode | Race between preflight and write is possible; older scp without `-s` fails. No claim of transactional remote directory sync. Authenticated SCP uses the same Vault handoff risks as exec. |
| Tunnel LAN exposure | Explicit loopback added by default, non-loopback requires `--yes`, dynamic needs approval, `ExitOnForwardFailure=yes`, local process list/stop | Remote `AllowTcpForwarding`, firewall and DNS affect exposure. Lifecycle belongs to running Broker; public binding needs operator review. Managed key guard persists with tunnel record. |
| Duplicate long-running/write execution | No automatic retry; task IDs, timeouts, cancellation and state; local disconnect states remain uncertain | A killed SSH process doesn't prove remote process death. Restart loses task records; detached systemd/tmux not implemented. Verify remotely before retrying. |
| sudo password exposure or SSH-password reuse | Independent typed `sudo-password`, new sudo-enabled `<alias>:sudo` naming with legacy/no-field bare-alias fallback, no argv, secure stdin, remove exact password from stdout/stderr | Legacy compatibility does not permit kind confusion. sudo/PAM may fail (`requiretty`); memory zeroization isn't absolute; AI must not guess or brute force. sudoers least privilege preferred. |
| Telnet mistaken for secure | Model and capabilities `encrypted=false`, `insecure_acknowledged` required, INSECURE UI text, dedicated error, audit transport where applicable | Telnet network automation isn't implemented. Future implementation must treat credentials/commands/output as plaintext. |
| Backup includes runtime/platform state or plaintext imported keys | Payload is config plus encrypted Vault envelope; independent backup password; imported SSH passwords/passphrases/private keys/sudo remain encrypted; exclude DEK plaintext, unlock state, sockets, approvals, sessions, caches/logs | Original Vault master password remains required after restore. External Agent/platform-bound/private hardware keys are not exported. Atomicity is per-file, not a two-file transaction. |
| Weak permissions/torn writes | Private directories/temp files, Unix `0600` private files and permission check, atomic replace, config/restore pre-change backups | Non-Unix helpers do not establish equivalent native Windows ACLs; multi-file crashes and same-user tampering need external protection. Windows permission/authentication behavior requires separate verification. |

## Approved future controls

L2: dedicated OS-user Broker and restricted socket, isolated human approval, with Secret/ASKPASS/private-key handling redesigned across that actual OS boundary. L3: SSH CA/short-lived certificates, separate identities, remote enforcement and centralized audit. Native Hello/Touch ID must release keys through TPM/Keychain cryptographic operations, not a boolean check followed by reading a plaintext DEK.

## Security invariants for tests and reviews

No real production credentials or servers in tests; no fabricated build/audit/cross-platform result; no automatic write retry; no secret values in argv/helper environment/logs/metadata audit; stdout/stderr remain separate; unknown hosts and unexpected ASKPASS prompts fail closed; registered authentication is re-resolved by Broker; imported keys are bounded regular files and temporary-key guards cover all OpenSSH paths; remote output is untrusted; explicit capabilities are returned for unsupported shells/protocols.

The current working tree passed its Windows native Rust checks/build and the complete isolated Linux fake/PTY/real-sshd/sudo/cleanup driver on 2026-11-08, including Vault password/encrypted-key exec and SCP. These results are source- and environment-specific. Native Windows permission/real authentication, every Vault task/tunnel/interactive path, forced-termination cleanup, and broader error matrices remain **NOT_RUN**, as detailed in `TESTING.md`; no independent security audit or universal compatibility claim follows.
